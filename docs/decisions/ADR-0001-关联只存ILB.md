# ADR-0001：关联数据只存在 ILB，本扩展不建副本

- 状态：已采纳（2026-11-02）
- 关联需求：需求 §3.3、§4；审计 §3、§9

## 背景

"角色卡 ↔ 世界书"的关联可以存在三个地方：本扩展自己的 `extension_settings`、酒馆角色卡的
`data.extensions.world`（原生绑定字段）、ILB 的 `bindings`。

酒馆原生字段表达的是"这张卡默认开哪些原生世界书"，语义不同；写进去会污染原生行为，也会和
ILB 自己的关联规则打架。本扩展自存一份则必然出现"两处数据打架、以谁为准"的问题。

## 可选方案

1. 本扩展自存一份关联（快，但与 ILB 的运行态会分叉）
2. 写进角色卡 `data.extensions.world`（能跟卡走，但改变了原生语义，且导入包会污染别人的卡）
3. 只存 ILB `bindings`，本扩展每次现查（慢一点，只有一个真相）

## 决定

采用方案 3。

- 关联的增删改全部走 `ILB.api.bindings.*`
- 界面上的"这本书还在不在""是不是孤儿"每次现查，不缓存
- 导出时从 `bindings.list` 读出关联，导入时用 `bindings.create` 写回

## 原因

- ILB 0.28.0 起关联已经参与判定（`resolveBooks` 会读 bindings），是运行时的唯一来源
- 一份数据只有一个真相，界面不可能显示"已关联"而实际没关联
- 角色卡被复制/改名时，ILB 自己会迁移关联（renameCharacter / 孤儿标记），本扩展跟着受益

## 影响

- 本扩展离开 ILB 不能工作（这是设计前提，不是缺陷）
- `ILBCC` 的关联页每次打开都要一次 `worldbooks.list` + `bindings.list`（几十本书量级，可忽略）

## 约束与重新审视条件

- 若 ILB 将来允许"离线编辑关联"，需要重新评估是否要本地草稿层
- 若出现"没装 ILB 也要管理关联"的需求，本 ADR 需重开
