## 1. 我理解的需求

### 1.1 三层分工

| 层 | 负责 | 明确不负责 |
|---|---|---|
| SillyTavern 原生 | 角色卡、原生世界书、原生导入导出、当前角色/聊天/群聊/Persona 上下文、原生世界书绑定与触发 | ILB 书与逻辑 |
| ILB Core | ILB 世界书、条目、逻辑、变量、运行时、书的导入导出 | 角色卡管理、角色卡包 |
| 本扩展 | 角色卡 ↔ ILB 书的多对多关联、`.ilbchar.json` 打包/拆包、关联有效性检查、把「当前角色」翻译成 ILB 可用的运行状态 | 替代原生卡管理、改原生按钮、直接读写 ILB 存档 |

一句话：本扩展是**资源组合与分发层**，不是第二个角色卡管理器，也不是第二个世界书引擎。

### 1.2 三条硬边界（验收里最容易破的）

1. **不改酒馆原生的角色卡导入/导出按钮和流程**；本扩展是并列的独立入口。
2. **不直接访问 ILB 内部存储**（`extension_settings.independent_lorebook`），只走 `ILB.api`。
3. **不把 ILB 关联写进原生卡的世界书绑定字段**（`data.extensions.world`、`world_info.charLore` 等）。原生绑定和 ILB 关联是两层数据，必须分开存、分开显示。

### 1.3 把验收标准翻译成可测行为

| 验收 | 可测行为 |
|---|---|
| 读当前角色及稳定身份 | 切换角色后，扩展拿到的 `avatar` 与 `characters` 中一致；重命名后关联仍指向同一张卡 |
| 关联一本书 / 多本书 | 关联列表可增删；刷新页面、重启酒馆后仍在 |
| 切换角色后运行态正确 | 生成时实际注入的书中，包含当前角色关联的书，不包含其他角色专属书 |
| 打包 / 拆包 | 导出的包重新导入后，角色、书、关联三者都能恢复；书里的逻辑/变量不丢 |
| 重复导入不静默覆盖 | 同名书/同名角色默认让用户选，且「覆盖」必须逐项确认 |
| 异常与部分失败 | 每一步的 成功/失败/跳过 都能列出来；失败后能重试或清理 |
| 不影响原生 | 不装本扩展时原生功能完全不变；装了之后原生按钮行为不变 |

### 1.4 术语（后面统一这么用）

- **原生绑定**：酒馆自己的世界书关联（全局、角色主书/额外书、Persona、聊天、群聊成员）。
- **ILB 关联**：本扩展要维护的「角色卡 ↔ ILB 书」关系，存在 ILB 侧。
- **启用策略**：书本身的三档策略（自动 / 始终 / 手动）和强制覆盖（自动 / 强制开 / 强制关）。
- **运行态**：这一次生成，ILB 实际判定这本书「启用了没有、因为什么」。

## 2. ILB 现状（0.27.0 / 接口 1.3）

### 2.1 结构

- 入口 `extension/index.js` 装配 repository / pipeline / api / panel / shell。
- `extension/core/` 是纯函数，`extension/adapters/` 是宿主边界，`extension/runtime/` 是对外与编排。
- 存档在 `extension_settings.independent_lorebook`，键为 `version/settings/books/manualState/chatStates/importLog/ui/snapshots/stats/logicGroups/logics`。**没有 `bindings` 键**。
- 书的数据形状见 `extension/core/model.js` 的 `defaultBook`：`activation.{mode,strategy,override,characters,manual}`、`host.{nativeNames,aliases,lastMatchedAt}`、`pool.share`、`entries`、`logic`、`_source`。**书没有 `enabled` 字段。**

### 2.2 现有启用判定（`extension/core/resolve-books.js`）

优先级从高到低：

1. 扩展点 `activationProviders` 的返回值（`runtime/registry.js`）
2. 书的 `activation.override = 'off'`
3. 书的 `activation.override = 'on'`
4. `activation.strategy = 'always'`
5. `activation.strategy = 'auto'`：用 `core/host-context.js` 的 `matchBookToHost` 匹配六类来源（全局 / 角色主书 / 角色额外书 / Persona / 当前聊天 / 群聊成员）；**只有书名相同算 candidate，不启用**，必须有真实绑定来源
6. 兜底：`legacyCharacterMode`（`activation.characters` 白名单 + 书名），只在拿不到 hostContext 时走

`HostContext` 已经带了 `character.avatar` 和 `group.members[].avatar`——**这正是做「角色 ↔ 书」关联需要的键**，不需要再改 ST 侧读取逻辑。

### 2.3 `ILB.api` 1.3 有什么、缺什么

已有（`extension/runtime/api.js`，`API_VERSION = '1.3'`）：

`snapshot / set / remove / call / callAsync / ui / subscribe / outcome / byId / nonce / context / strict / vars / caps / ready / worldbooks`

`worldbooks`：

| 方法 | 返回 |
|---|---|
| `list({detail})` | `{ok, books:[{id,name,enabled,entries,logics,updatedAt,schemaVersion,book?}]}` |
| `get(id)` / `has(id)` | `{ok, book}` / `{ok, exists}` |
| `exportBook(id)` | `{ok, schema_version, exported_at, book}`，深拷贝 |
| `importBook(payload,{onConflict,targetId})` | `{ok,id,action}`；`onConflict`：`new/skip/overwrite/ask` |
| `importMany({books},opts)` | 逐本结果 + `failed[]` |

失败统一 `{ok:false,error:{code,message}}`，`code` 为 `NOT_FOUND / CONFLICT / BAD_PAYLOAD / NOT_SUPPORTED`，不抛异常。

**缺**（对本项目是硬缺口）：

- 没有 `bindings`（角色 ↔ 书）的任何读写接口。
- 没有 `runtime.status/preview`：拿不到「这次生成实际判定了什么、为什么」。
- 没有 `worldbooks.deleteBook`：导入部分失败时无法清理创建出来的书。
- 没有修改书 `activation` 的接口：三态策略只能靠书本身策略 + 新关联共同表达。
- `worldbooks.list` 的 `enabled` 是 `book.enabled !== false`，书没有这个字段，所以**恒为 true**，不是运行态。
- `importBook` 不校验 `schema_version`、不走迁移（`adapters/repository.js` 的 `importBook` 直接 `normalizeBook`）。
- `exportAll/importAll`（`adapters/repository.js:481-529`）按白名单复制字段，**新增的 `bindings` 如果不同步加进去，整份备份/恢复会丢关联**。

### 2.4 路线图原话

> 下一步：bindings（角色卡 ↔ 多书）、runtime.context/status/setOverride（P1），然后才做角色卡兼容扩展。
> —— `D:\文档\1\DSH\ILB\docs\开发规划-现阶段.md:691`

也就是说：**本扩展的运行时能力，ILB 侧本来就计划先做。**

## 4. 能力缺口（按严重度）

| 编号 | 缺什么 | 后果 | 谁改 |
|---|---|---|---|
| G1 | 没有「角色 ↔ 书」关联的持久化/查询 API | 关联无处可存；需求 §3.3 不成立 | ILB |
| G2 | 没有运行时状态/预览 API | 无法验证「书真的参与了生成」；需求 §3.4 验收第 8 条不成立 | ILB |
| G3 | 没有 `deleteBook` | 导入部分失败后无法清理，只能让用户手动删 | ILB |
| G4 | 没有改书 `activation` 的 API | 三态只能落在关联记录上；无法从本扩展改书策略 | 设计规避（关联三态） |
| G5 | `worldbooks.list` 的 `enabled` 不实 | 扩展若拿它当运行态会显示错 | ILB 文档/字段修正 |
| G6 | `importBook` 不校验/迁移 `schema_version` | 导入了旧格式书可能字段缺失 | ILB |
| G7 | `avatar` 改名会变；`characters` 可能 shallow | 关联失效/读不到 `data` | 本扩展 + ILB 迁移钩子 |

**其中 G1、G2、G3 是阻塞项。** 不解决它们，「跟随角色启停」只能做成「UI 上显示已启用」，而需求明确禁止这种假实现。

## 5. 方案比较

### 方案 A（推荐）：ILB 先补 P1，再做本扩展

ILB 侧新增（保持「只增不改」）：

- `core/bindings.js`：纯函数，规范化记录、按 avatar 取当前角色、计算关联投票。
- `adapters/repository.js`：`bindings` 的 CRUD + 按角色/按书查询 + 改名迁移 + 孤儿标记；`exportAll/importAll` 带上 `bindings`。
- `core/resolve-books.js`：在「书级强制」之后、「策略」之前插入关联规则。
- `runtime/pipeline.js`：把 `bindings` 传进 resolve；`describeLastRun` 带出关联命中。
- `runtime/api.js`：`API_VERSION 1.4`；`caps` 加 `bindings/runtime/bookDelete`；新增：
  - `bindings.list({character?,bookId?})`、`bindings.get(id)`、`bindings.create({character:{avatar,name},bookId,policy})`、`bindings.update(id,{policy,note})`、`bindings.remove(id)`、`bindings.removeForCharacter(avatar)`、`bindings.renameCharacter(oldAvatar,newAvatar)`
  - `runtime.preview()`（当前上下文下的解析结果，不跑逻辑、不注入）、`runtime.status()`（最近一次生成的实际结果）
  - `worldbooks.deleteBook(id)`（带 `force` 确认）
- `adapters/sillytavern-events.js`：`CHARACTER_RENAMED` 迁移、`CHARACTER_DELETED` 标记孤儿（不自动删）。
- 文档：`docs/UI扩展接口.md`、`docs/世界书接口.md`、`CHANGELOG.md`、`docs/决策记录.md` 新增一条 ADR。
- 测试：core 纯函数、resolve 优先级、API 契约、备份往返。

本扩展侧只做：识别、关联 UI、打包/拆包、导入编排、诊断。**不复制 ILB 的解析逻辑。**

- 满足验收：12/12
- 工作量：ILB P1 约 1~2 天；本扩展 v1 约 3~5 天
- 风险：要改 ILB 本体，需遵守 ILB 自己的发布流程

### 方案 B：只加一个「公开的 activationProviders 注册口」

ILB 只加 `api.activation.registerProvider(id, fn)`，关联存在本扩展自己的 `extension_settings` 里。

- 优点：ILB 改动最小（约半天）
- 缺点：关联不在 ILB 存档里，ILB 书架看不到、ILB 整份备份不包含；不符合需求「关联数据通过 ILB Core 公开 API 保存」；两套数据源容易打架
- 满足验收：关联存储这条不满足（其余可）

### 方案 C：v1 只做打包/拆包

完全不动 ILB 运行时，只做「角色卡 + 书 + 关联清单」的导入导出；启停仍靠用户手动/ILB 现有策略。

- 满足验收：第 1、2、3、5、6、7、9、10、12 条可满足；第 4、8 条不满足
- 适合：先验证包格式和导入流程，运行时等 ILB P1

**建议：A。** 如果暂时不想动 ILB，就先按 C 做包格式（不与 A 冲突），把运行时留到 ILB 更新后。

## 6. 推荐架构（方案 A）

### 6.1 模块

```text
ILB Character Compatibility/
├── manifest.json
├── index.js                 # 启动、等 ILB ready、挂 UI、注册事件
├── src/
│   ├── ilb-client.js        # 只封装 ILB.api，检查 caps/版本，统一错误文案
│   ├── identity.js          # 角色识别：avatar 优先、shallow 时补全、改名迁移
│   ├── bindings.js          # 关联的增删查（调 ILB bindings API）
│   ├── package-format.js    # 包的读写、版本检查、校验
│   ├── export-service.js    # 导出编排
│   ├── import-service.js    # 导入编排 + 失败矩阵 + 清理
│   ├── ui/                  # 三个页签
│   └── diagnostics.js       # 环境/关联/运行态检查
├── styles/
└── i18n/
```

约束：**本扩展不 import ILB 的任何文件**（ILB 的 `docs/交接-UI扩展.md` 明写两个扩展没有稳定加载顺序），只通过 `ILB.api`。

### 6.2 关联记录

```js
{
  id: 'bind-<random>',
  character: { avatar: 'A.png', name: 'A' },  // avatar 是键，name 只用于显示
  bookId: 'book-...',
  policy: 'auto' | 'on' | 'off',              // 跟随 / 强制启用 / 强制停用
  note: '',
  createdAt: 0,
  updatedAt: 0,
  orphanedAt: null                            // 角色删除后标记，不自动清
}
```

- 唯一性：`(character.avatar, bookId)` 只能有一条。
- 改名：`CHARACTER_RENAMED` 时批量改 `character.avatar/name`；`CHARACTER_DUPLICATED` 不自动复制关联（避免误扩）。
- 删书：`worldbooks.delete` 后把相关关联标孤儿，UI 提示「书已不存在，可清理」。

### 6.3 运行时优先级（建议）

按顺序，第一条命中即生效：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 书 `override=off` | 停 |
| 2 | 书 `override=on` | 启 |
| 3 | 当前角色（群聊为所有启用成员）对该书有 `policy=off` | 停 |
| 4 | 当前角色对该书有 `policy=on` | 启 |
| 5 | 书 `strategy=always` | 启 |
| 6 | 书 `strategy=auto` 且（原生匹配 或 关联 `policy=auto`） | 启 |
| 7 | 书 `strategy=manual` 且关联 `policy=on` | 启 |
| 8 | 其余 | 停 |

群聊合并规则：

- 取所有「启用成员」的关联做并集；`on` 优先于 `off`；只有全部成员都 `off` 才停。
- 成员卡不存在时忽略该成员，不报错。

Persona 只影响 ILB 现有的原生匹配（`persona` 来源），**不参与**角色关联的投票——满足「切换 Persona 不应覆盖角色关联」。

> 这条优先级是建议值，需要你确认（见 §10 Q3）。特别是「关联强制停用」是否应该压过书的「始终启用」。

### 6.4 触发点

- **正确性靠 ILB**：每次生成前 ILB 自己 `readHostContext` + `bindings` 解析，不依赖本扩展的事件是否及时。这样切角色、切聊天、切 Persona、群聊都不会漏。
- **UI 刷新**：`CHAT_CHANGED`（切角色/聊天）、`CHARACTER_EDITED`、`CHARACTER_RENAMED`、`CHARACTER_DELETED`、`CHARACTER_DUPLICATED`、`GROUP_*`、`PERSONA_*`、`ilb:change`，统一 150ms 合并。
- 扩展自身**不做注入**，不碰 prompt。

```json
    "card": { "spec": "chara_card_v2", "spec_version": "2.0", "data": { } }
  },
  "worldbooks": [
    {
      "ref": "wb1",
      "name": "世界观设定",
      "book": { "schema_version": 2, "book_id": "book-...", "name": "世界观设定", "entries": [], "logic": [] }
    }
  ],
  "bindings": [
    { "book_ref": "wb1", "policy": "auto", "note": "" }
  ],
  "metadata": { "book_count": 1, "binding_count": 1 }
}
```

要点：

- `character.card` 用原生导出接口拿到的 V2 JSON（酒馆会按自己的规则去掉私有字段，这是既有行为），**不额外裁剪未知字段**；内嵌 `character_book` 保留在卡里，不另存。
- `worldbooks[].book` 用 `exportBook(id).book`，完整保留条目、逻辑、变量、`_source`、`host`。
- `bindings` 只引用包内 `ref`，**不引用导出端的 book_id**（`importBook` 用 `new` 会换 id）。
- 顶层 `format_version` 只认 1；`>1` 直接拒绝并说明「请升级扩展」，不猜。
- 书自身的 `schema_version` 也检查；`>2` 拒绝，`<2` 提示可能缺字段（ILB 导入不迁移）。

### 6.6 导出流程

1. 选角色卡（当前角色默认选中）。
2. 读全量卡：先 `getOneCharacter(avatar)`，再取 `characters` 里的对象。
3. 调 `bindings.list({character: avatar})` 拿关联；解析书名、标记失效。
4. 展示清单（书名、条目数、逻辑数、最后更新），允许取消勾选。
5. 逐本 `exportBook(id)`；任何一本失败 → 列出失败书名，**不生成半成品包**。
6. 调原生导出接口拿 V2 JSON（`POST /api/characters/export`，`format:'json'`）。
7. 组装、下载。**不写回角色卡、不写原生书、不改 ILB 书。**

### 6.7 导入流程

顺序很重要（因为无法回滚角色卡）：

1. 读文件 → JSON 解析 → 检查 `format` / `format_version` / 必填字段 → 失败即停。
2. 检查包内书：`schema_version`、`book_id` 是否与现有书冲突（`worldbooks.list({detail:true})` 按 `book_id`/`name`）。
3. 预览：将新建/跳过/覆盖哪些书、将新建哪个角色（同名会加后缀）、将建立哪些关联。
4. 用户确认。
5. **先导书**：逐本 `importBook(book, {onConflict})`；默认 `ask`，用户可选 `new/skip/overwrite`。记录每本的实际 `id`。
6. **再导角色**：`POST /api/characters/import`，`file_type=json`，**不传 `preserved_name`**；拿到 `file_name` 作为新 avatar。
7. `getCharacters()` 刷新，按 avatar 找到新卡。
8. 用第 5 步的实际书 id + 第 6 步的 avatar，逐条 `bindings.create`。
9. 校验：`bindings.list({character: newAvatar})` 数量与预期一致；`runtime.preview()` 能看到这些书（如果 ILB 已支持）。
10. 展示结果：成功 / 跳过 / 失败 / 孤儿书 / 可重试项 / 清理入口。

失败矩阵：

| 失败点 | 已产生的东西 | 处理 |
|---|---|---|
| 第 1~3 步 | 无 | 直接报错，不改任何数据 |
| 第 5 步部分书失败 | 前面成功的书 | 停止导角色；列出已建书；提供「删除本次已建的书」（需 G3）或「保留，稍后重试」 |
| 第 6 步角色失败 | 全部书已建 | 同上；**不自动删角色** |
| 第 8 步部分关联失败 | 角色 + 书都在 | 列出未关联成功的书，提供重试；不显示整体成功 |
| 第 9 步校验不一致 | 同上 | 标红，写诊断日志 |

### 6.8 UI

三个页签，放在扩展设置抽屉里：

- **关联**：当前角色（头像+名字+avatar）、关联书列表（书名/条目数/策略下拉/有效性/移除）、添加书（搜索+多选）、「在 ILB 中打开」。
- **导入 / 导出**：导出（选角色→勾书→确认→下载）；导入（选文件→预览→逐本冲突选择→确认→结果）。
- **诊断**：ILB 是否安装、API 版本/caps、`api.ready`、当前角色识别、关联总数/孤儿数、最近一次运行态（`runtime.status`）、最近导入导出记录。技术细节默认折叠。

不做花哨动效；失败一律红字+具体书名/角色名，不用「操作失败」四个字打发。

### 6.9 诊断与日志

- 每次导入/导出在扩展自己的 `extension_settings` 里存最近 20 条记录（时间、动作、包名、成功/失败数）。
- 不记录书内容、不记录聊天内容。
- 关联数据以 ILB 为准，本扩展不另存副本（避免两套真相）。

## 9. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 改 ILB 本体涉及发布流程 | 排期不可控 | 先只做「只增不改」的 API；版本号 1.3→1.4，caps 判定 |
| `avatar` 改名竞态 | 关联指向旧名 | ILB 在 `CHARACTER_RENAMED` 同步迁移；本扩展 UI 兜底修复 |
| 导入部分失败无法回滚 | 孤儿书/孤儿角色 | 先导书后导角色；提供清理；绝不静默成功 |
| `preserved_name` 覆盖同名卡 | 数据丢失 | 默认不传；覆盖只在用户明确选择时做，且先检测 |
| ST 版本差异（1.12→1.19） | 事件/字段变化 | 只用 `getContext()`、公开事件、HTTP 路由；启动时自检 |
| 大包卡 UI | 导入导出卡死 | 分片、进度条、`await` 让帧 |
| 包是外部输入 | 注入/坏数据 | 严格 schema 校验；不 `eval`；不拼 HTML |
| 两套关联数据源 | 冲突 | 只存 ILB；本扩展不落副本 |
